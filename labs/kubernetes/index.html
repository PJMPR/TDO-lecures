Laboratorium 03 / Kubernetes

Przenieś Mission Control z Compose do Kubernetes

Otrzymujesz działającą aplikację Angular + ASP.NET Core + MySQL wraz z Docker Compose. Twoim zadaniem jest opisać jej stan w manifestach Kubernetes, uruchomić lokalnie w Rancher Desktop i udowodnić odporność rozwiązania.

Cel i sposób pracy

Nie przepisujesz aplikacji. Migrujesz sposób jej uruchamiania. Compose pozostaje punktem odniesienia, a katalog k8s/ tworzysz samodzielnie.

Composedb + api + frontendenvironmenthealthchecknamed volume
→
KubernetesDeployments / ServiceConfigMap / SecretprobesPVC
  • Wykonuj zadania po kolei i commituj małe zmiany.
  • Po każdym kubectl apply sprawdzaj stan oraz zdarzenia.
  • Nie używaj gotowych generatorów pełnego rozwiązania. Szkielety wymagają uzupełnienia.
  • Dane i hasła są wyłącznie lokalne. Nie publikuj prawdziwych sekretów.
Ważne: Kubernetes nie interpretuje compose.yaml. Nazwy usług, zmienne, porty, healthcheck i wolumen trzeba świadomie przełożyć na obiekty API.

Co sprawdzić w Rancher Desktop i lokalnym klastrze?

Klaster Kubernetes to środowisko złożone z węzłów i komponentów sterujących, które uruchamia oraz nadzoruje zadeklarowane zasoby. Rancher Desktop uruchamia na laptopie zarówno silnik kontenerów, jak i lokalny Kubernetes. Zielony status aplikacji nie oznacza jeszcze, że wszystkie zasoby Mission Control działają. Najpierw sprawdź środowisko, a później obserwuj obiekty utworzone przez własne manifesty. Wróć do słowniczka ↑

1. W aplikacji Rancher Desktop

  • Kubernetes jest włączony i ma stan Running. Po restarcie lub aktualizacji poczekaj, aż inicjalizacja się zakończy.
  • Container engine to dockerd (moby). Laboratorium zakłada, że obrazy zbudowane poleceniem docker compose są dostępne także dla lokalnego klastra.
  • Przydzielono wystarczające zasoby — zalecane minimum dla ćwiczenia to 6 GB pamięci. Zbyt mała ilość pamięci może powodować restarty i Pody w stanie Pending.
  • Obrazy lokalne istnieją: po wykonaniu zadania 1 powinny być widoczne tagi mission-control-api:1.0.0 oraz mission-control-frontend:1.0.0.
  • Nie trwa reset ani aktualizacja klastra. Reset Kubernetes usuwa zasoby laboratoryjne i może usunąć dane z lokalnego storage.

3. Co obserwować podczas wykonywania zadań?

kubectl get pods -n mission-control -o wide
kubectl get deployment,service -n mission-control
kubectl get endpointslice -n mission-control
kubectl get pvc -n mission-control
kubectl get ingress -n mission-control
kubectl get events -n mission-control --sort-by=.lastTimestamp
  • READY — liczba gotowych kontenerów, np. 1/1. Sam stan Running nie gwarantuje gotowości do obsługi ruchu.
  • RESTARTS — rosnąca wartość może oznaczać błąd aplikacji, sondy lub brak pamięci.
  • Service i EndpointSlice — EndpointSlice przechowuje aktualną listę adresów gotowych Podów wybranych przez Service. Service bez endpointów nie ma Podów, do których może wysłać żądanie. Wróć do słowniczka ↑
  • PVC — przed uruchomieniem API sprawdź, czy wolumen bazy ma stan Bound.
  • Events — tutaj najczęściej znajdziesz przyczynę Pending, błędnego obrazu, niedziałającej sondy lub problemu z wolumenem.
Nie naprawiaj przez reset klastra: najpierw użyj get, describe, Events i logów. Reset Rancher Desktop usuwa objawy razem ze środowiskiem, ale nie wyjaśnia przyczyny błędu i może skasować wyniki ćwiczenia.

Konfiguracja

Zadanie 4 — ConfigMap i Secret

ConfigMap przechowuje konfigurację niewrażliwą, np. nazwę bazy lub użytkownika. Secret służy do oddzielenia danych wrażliwych, np. haseł, od obrazu i manifestu Deploymentu. Nie wpisuj hasła w Deployment API ani bazy. Wróć do słowniczka ↑

  1. Dodaj ConfigMap z nazwą bazy i użytkownikiem.
    Pokaż przykład konfiguracji

    W sekcji data dodaj np. MYSQL_DATABASE: mission_control i MYSQL_USER: mission_user.

  2. Dodaj Secret z lokalnymi hasłami ćwiczeniowymi.
    Pokaż przykład konfiguracji

    Użyj type: Opaque i sekcji stringData z kluczami MYSQL_PASSWORD oraz MYSQL_ROOT_PASSWORD. Nie commituj prawdziwych danych dostępowych.

  3. Zastosuj i sprawdź oba zasoby.
    Pokaż przykład polecenia

    Wykonaj kubectl apply -f k8s/10-config.yaml, a następnie kubectl get configmap,secret.

# 10-config.yaml — szkielet
apiVersion: v1
kind: ConfigMap
metadata:
  name: mission-config
  namespace: mission-control
data:
  MYSQL_DATABASE: ...
  MYSQL_USER: ...
---
apiVersion: v1
kind: Secret
metadata:
  name: mission-secret
  namespace: mission-control
type: Opaque
stringData:
  MYSQL_PASSWORD: ...
  MYSQL_ROOT_PASSWORD: ...
kubectl apply -f k8s/10-config.yaml
kubectl get configmap,secret
kubectl describe configmap mission-config
kubectl get secret mission-secret -o jsonpath="{.data.MYSQL_PASSWORD}"
Base64 nie jest szyfrowaniem: stringData ułatwia ćwiczenie, ale każdy z prawem odczytu Secret może poznać wartość. Używaj wyłącznie danych lokalnych.

Sprawdź w Rancher Desktop

  1. W Cluster Dashboard wybierz Namespace mission-control.
  2. Otwórz zasoby ConfigMaps i znajdź mission-config.
  3. Otwórz zasoby Secrets i znajdź mission-secret.

Oczekiwany widok: ConfigMap ma dwa klucze konfiguracyjne, a Secret trzy klucze. Dashboard może ukrywać wartości Secret — nie jest to błąd.

Dane

Zadanie 5 — MySQL, Service i PVC

PVC (PersistentVolumeClaim) to żądanie trwałego miejsca na dane, które Pod może zamontować jako wolumen. W tym ćwiczeniu uruchamiamy MySQL w Kubernetes, aby przećwiczyć PVC, Service, Secret, sondy oraz odtworzenie Poda bez utraty danych. Poniższy układ — jeden Deployment, jeden Pod i lokalny PVC — jest odpowiedni do nauki i środowiska developerskiego, ale nie zapewnia wysokiej dostępności ani ochrony przed awarią węzła lub storage. PVC utrzymuje dane poza cyklem życia Poda, lecz nie jest backupem. W systemie produkcyjnym zwykle wybiera się zarządzaną bazę poza klastrem albo dojrzały operator bazy, replikację, zewnętrzne backupy i regularnie testowane odtwarzanie. Nie kopiuj tego manifestu bezpośrednio jako architektury produkcyjnej. Wróć do słowniczka ↑
  1. Dodaj PVC żądające 1Gi w domyślnej StorageClass.
    Pokaż przykład konfiguracji

    Ustaw accessModes: [ReadWriteOnce] oraz resources.requests.storage: 1Gi. Pomiń storageClassName, aby użyć klasy domyślnej.

  2. Dodaj Service db typu ClusterIP na porcie 3306.
    Pokaż przykład konfiguracji

    Service powinien mieć selector.app: db, port: 3306 i targetPort: 3306. Pod musi mieć odpowiadającą etykietę.

  3. Dodaj jedno-replikowy Deployment db z obrazem mysql:8.4.
    Pokaż kluczowe pola

    Ustaw replicas: 1, nazwę kontenera db i image: mysql:8.4.

  4. Wczytaj ConfigMap i Secret przez envFrom.
    Pokaż przykład konfiguracji

    W kontenerze dodaj envFrom z configMapRef.name: mission-config oraz secretRef.name: mission-secret.

  5. Zamontuj PVC w /var/lib/mysql.
    Pokaż przykład konfiguracji

    W volumeMounts użyj mountPath: /var/lib/mysql, a w volumes wskaż persistentVolumeClaim.claimName: mysql-data. Nazwy wolumenu muszą być identyczne.

  6. Przepisz healthcheck Compose na readiness i liveness probe typu exec.
    Pokaż przykład sondy

    Komenda może wykonać mysqladmin ping -h 127.0.0.1 -uroot -p$MYSQL_ROOT_PASSWORD. Daj liveness większe initialDelaySeconds niż readiness.

# 20-database.yaml — kontrakt, nie pełne rozwiązanie
kind: PersistentVolumeClaim
# accessModes: [ReadWriteOnce], requests.storage: 1Gi
---
kind: Service
# name: db, port: 3306
---
kind: Deployment
# replicas: 1, image: mysql:8.4
# envFrom: mission-config + mission-secret
# volumeMounts + volumes.persistentVolumeClaim
# readinessProbe/livenessProbe: mysqladmin ping
kubectl apply -f k8s/20-database.yaml
kubectl get pvc,pods,service
kubectl describe pod -l app=db
kubectl logs -l app=db --tail=100

Pod jest najmniejszą jednostką uruchamianą przez Kubernetes; zawiera jeden lub więcej współdzielących sieć i wolumeny kontenerów. Service zapewnia stabilną nazwę DNS i adres dla zmiennego zbioru Podów wybranych etykietami. Sprawdź: PVC ma stan Bound, Pod bazy jest Ready, a Service ma endpoint. Nie skaluj tej prostej bazy do wielu replik — współdzielony katalog MySQL nie tworzy klastra bazy. Zwiększenie pola replicas nie konfiguruje replikacji MySQL i może prowadzić do konfliktów lub uszkodzenia danych. Wróć do słowniczka ↑

Sprawdź w Rancher Desktop

  1. W Cluster Dashboard → Workloads otwórz Deployment db i jego Pod.
  2. W sekcji storage/PVC znajdź mysql-data.
  3. W sekcji Services znajdź Service db.
  4. Opcjonalnie otwórz ten Pod również w widoku Containers, aby zobaczyć log startu MySQL, zmienne środowiskowe i zamontowany wolumen.

Oczekiwany widok: Deployment 1/1, Pod Running/Ready, PVC Bound oraz Service ClusterIP na porcie 3306.

Backend

Zadanie 6 — Deployment i Service API

Deployment deklaruje oczekiwaną liczbę replik aplikacji, tworzy zarządzające nimi ReplicaSety oraz kontroluje aktualizacje. Gdy Pod zniknie, kontroler dąży do odtworzenia zadeklarowanego stanu. Wróć do słowniczka ↑

  1. Dodaj Deployment api z dwiema replikami obrazu mission-control-api:1.0.0.
    Pokaż kluczowe pola

    Ustaw replicas: 2, nazwę kontenera api oraz image: mission-control-api:1.0.0.

  2. Ustaw imagePullPolicy: Never i port kontenera 8080.
    Pokaż przykład konfiguracji

    Dodaj imagePullPolicy: Never oraz nazwany port: name: http, containerPort: 8080.

  3. Zbuduj connection string ze zmiennych ConfigMap/Secret. Hostem jest Service db, nie localhost.
    Pokaż bezpieczniejszy wariant

    Przechowaj cały lokalny connection string pod kluczem ConnectionStrings__MissionDb w Secret i wczytaj przez secretKeyRef. Wartość zaczyna się od Server=db;Port=3306;.

  4. Dodaj readiness probe, która decyduje, czy Pod może otrzymywać ruch, oraz liveness probe, która wykrywa zawieszony kontener i może spowodować jego restart. Obie sondy HTTP kieruj na /health. Wróć do słowniczka ↑
    Pokaż przykład konfiguracji

    Dla obu sond ustaw httpGet.path: /health i httpGet.port: http. Liveness może mieć initialDelaySeconds: 20.

  5. Dodaj requests i limits.
    Pokaż przykładowe wartości

    Na start użyj requests cpu: 100m, memory: 128Mi oraz limits cpu: 500m, memory: 256Mi.

  6. Dodaj ClusterIP Service api: port 8080 → targetPort 8080.
    Pokaż przykład konfiguracji

    Użyj selector.app: api, port: 8080 i targetPort: http, jeśli port kontenera został nazwany http.

# kluczowe pola 30-api.yaml
containers:
  - name: api
    image: mission-control-api:1.0.0
    imagePullPolicy: Never
    ports:
      - {name: http, containerPort: 8080}
    env:
      - name: ConnectionStrings__MissionDb
        value: "Server=db;Port=3306;Database=...;User=...;Password=..."
    readinessProbe:
      httpGet: {path: /health, port: http}
    resources:
      requests: {cpu: 100m, memory: 128Mi}
      limits: {cpu: 500m, memory: 256Mi}

Szkielet pokazuje strukturę, ale nie spełnia wymogu Secret, dopóki nie zbudujesz wartości bez ujawniania hasła. Możesz przekazać cały connection string jako jeden klucz Secret albo użyć osobnych zmiennych i zmienić sposób konfiguracji aplikacji.

kubectl apply -f k8s/30-api.yaml
kubectl rollout status deployment/api
kubectl get pods -l app=api -o wide
kubectl port-forward service/api 8080:8080
curl.exe http://localhost:8080/health

Sprawdź w Rancher Desktop

  2. Sprawdź liczbę dostępnych replik oraz listę należących do niego Podów.
  3. W sekcji Services otwórz api i sprawdź port 8080.
  4. W widoku Containers otwórz jeden kontener API i zakładkę Logs.

Oczekiwany widok: Deployment 2/2, dwa gotowe Pody z obrazem 1.0.0, Service ClusterIP i log Application started.

Frontend

Zadanie 7 — Deployment i Service frontendu

Nginx w obrazie przede wszystkim serwuje zbudowane pliki Angulara. Ma również regułę proxy /api → api:8080, potrzebną w Docker Compose i przy awaryjnym port-forward. W następnym zadaniu ruch wchodzący do klastra rozdzieli bezpośrednio Traefik.

  1. Dodaj Deployment frontend z dwiema replikami.
    Pokaż kluczowe pola

    Ustaw metadata.name: frontend, replicas: 2 oraz jednakowe app: frontend w selektorze i etykietach szablonu Poda.

  2. Użyj obrazu mission-control-frontend:1.0.0 i imagePullPolicy: Never.
    Pokaż przykład konfiguracji

    Kontener może nazywać się frontend; ustaw obraz z jawnym tagiem, politykę Never i port kontenera 80 nazwany http.

  3. Dodaj sondy HTTP na / oraz zasoby.
    Pokaż przykład konfiguracji

    W readiness i liveness użyj httpGet.path: / oraz port: http. Przykładowe requests to 50m/64Mi, a limits 200m/128Mi.

  4. Dodaj ClusterIP Service frontend na porcie 80.
    Pokaż przykład konfiguracji

    Service powinien wybierać app: frontend i mapować port: 80 na targetPort: http.

kubectl apply -f k8s/40-frontend.yaml
kubectl rollout status deployment/frontend
kubectl get deployment,replicaset,pods,service
kubectl port-forward service/frontend 8088:80

Port-forward tworzy tymczasowy tunel z portu komputera do Poda lub Service w klastrze; działa tylko podczas działania polecenia i służy głównie do testów. Otwórz http://localhost:8088. Jeśli UI działa, ale /api zwraca 502, sprawdź nazwę Service API, port oraz logi nginx i backendu. Wróć do słowniczka ↑

Sprawdź w Rancher Desktop

  1. W Cluster Dashboard → Workloads otwórz Deployment frontend i potwierdź dwie repliki.
  2. W sekcji Services znajdź frontend.
  3. Otwórz w Rancher Desktop widok Port Forwarding, znajdź Service frontend, kliknij Forward i wybierz lokalny port 8088.

Oczekiwany widok: Deployment 2/2, dwa Pody nginx, Service na porcie 80 i aktywne przekierowanie na localhost. Jeśli port-forward działa już z terminala, nie uruchamiaj drugiego na tym samym porcie.

Ruch HTTP

Zadanie 8 — Ingress

Ingress opisuje reguły kierowania zewnętrznego ruchu HTTP/HTTPS do Service na podstawie hosta i ścieżki. Chcemy uzyskać jeden punkt wejścia do aplikacji. Traefik odbierze żądanie HTTP i na podstawie ścieżki wybierze właściwy Service. Dzięki temu nginx frontendu nie pośredniczy w normalnym ruchu do API. Wróć do słowniczka ↑

przeglądarka
     │
     ▼
Traefik / Ingress
     ├── /api, /health ──► Service api ──► Pody API
     └── /              ──► Service frontend ──► nginx + Angular
Czym jest Traefik? To reverse proxy działający w klastrze jako kontroler Ingress. Obserwuje manifesty Ingress i automatycznie tworzy z nich reguły routingu. W Rancher Desktop/K3s jest zwykle dostępny bez instalowania kolejnego proxy. Nginx pozostaje wewnątrz kontenera frontendu jako lekki serwer plików Angulara; Traefik zarządza ruchem wchodzącym do całej aplikacji. Wróć do słowniczka ↑
  1. Sprawdź, czy klasa traefik i jej Pod są dostępne.
    Pokaż przykład polecenia

    Wykonaj kubectl get ingressclass oraz kubectl get pods -n kube-system -l app.kubernetes.io/name=traefik.

  2. Dodaj Ingress dla hosta mission.local.
    Pokaż kluczowe pola

    Użyj apiVersion: networking.k8s.io/v1, ingressClassName: traefik i reguły z host: mission.local.

  3. Skieruj /api oraz /health bezpośrednio do Service api na port 8080.
    Pokaż przykład konfiguracji

    Dla /api ustaw pathType: Prefix, a dla /health — Exact. Oba backendy wskazują service.name: api i port 8080.

  4. Skieruj pozostałą ścieżkę / do Service frontend na port 80.
    Pokaż przykład konfiguracji

    Dodaj ścieżkę / z pathType: Prefix i backendem frontend:80. Umieść ją po bardziej szczegółowych ścieżkach.

  5. Przetestuj routing, podając nagłówek Host.
    Pokaż przykład polecenia

    Użyj curl.exe -H "Host: mission.local" http://127.0.0.1/health. Bez nagłówka Host reguła dla mission.local nie zostanie dopasowana.

# 50-ingress.yaml — szkielet
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: mission-control
  namespace: mission-control
spec:
  ingressClassName: traefik # albo inna klasa wskazana przez prowadzącego
  rules:
    - host: mission.local
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 8080
          - path: /health
            pathType: Exact
            backend:
              service:
                name: api
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
kubectl get ingressclass
kubectl get pods -n kube-system -l app.kubernetes.io/name=traefik
kubectl apply -f k8s/50-ingress.yaml
kubectl get ingress
curl.exe -H "Host: mission.local" http://127.0.0.1/
curl.exe -H "Host: mission.local" http://127.0.0.1/health
Plan B: jeśli lokalny Ingress nie działa, uruchom kubectl port-forward -n mission-control service/frontend 8088:80. W tym wariancie ruch omija Traefika, a nginx frontendu obsługuje Angulara i przekazuje /api do Service API. Pozwala to dokończyć laboratorium bez modyfikowania globalnej konfiguracji Rancher Desktop.
Co oznacza błąd webhooka nginx?

Komunikat failed calling webhook "validate.nginx.ingress.kubernetes.io" z brakiem Service ingress-nginx-controller-admission oznacza pozostałość po niekompletnej instalacji ingress-nginx. To problem klastra, nie manifestu aplikacji ani Traefika. Nie usuwaj globalnego webhooka w ramach zadania — zapisz błąd, użyj planu B i zgłoś go prowadzącemu.

Sprawdź w Rancher Desktop

  1. W ustawieniach Preferences → Kubernetes potwierdź, że opcja Enable Traefik jest włączona.
  2. W Cluster Dashboard otwórz zasoby Ingress i wybierz mission-control.
  3. Sprawdź host mission.local oraz trzy reguły ścieżek prowadzące do Service frontend i api.

Oczekiwany widok: Ingress jest aktywny i pokazuje backendy dla /, /api oraz /health. Jeśli obiektu nie ma po błędzie webhooka, użyj planu B i zachowaj komunikat do diagnozy.

Zadanie 9 — pełny przepływ i trwałość danych

  1. Dodaj misję przez UI.
    Pokaż wskazówkę

    Dodaj rekord z łatwo rozpoznawalną nazwą, np. test-pvc-01, aby jednoznacznie znaleźć go po restarcie bazy.

  2. Odczytaj ją przez /api/missions.
    Pokaż przykład polecenia

    Przy port-forward użyj curl.exe http://localhost:8088/api/missions; przy Ingress dodaj nagłówek Host: mission.local.

  3. Zapisz nazwę Poda bazy i usuń tylko ten Pod.
    Pokaż bezpieczny sposób

    Najpierw wykonaj kubectl get pods -l app=db. Skopiuj dokładną nazwę i przekaż ją do kubectl delete pod NAZWA — nie usuwaj Deploymentu ani PVC.

  4. Poczekaj na nowy Pod i sprawdź, czy rekord pozostał.

Sprawdź w Rancher Desktop

  3. Otwórz PVC mysql-data i potwierdź, że jest to ten sam zasób Bound.

Eksploatacja

Zadanie 10 — self-healing i skalowanie

  1. Obserwuj Pody w jednym terminalu.
    Pokaż przykład polecenia

    Uruchom kubectl get pods -w i pozostaw terminal otwarty. Opcja -w pokazuje kolejne zmiany stanu.

  2. Usuń jeden Pod API i zmierz czas odtworzenia.
    Pokaż sposób wykonania

    W drugim terminalu znajdź Pod przez kubectl get pods -l app=api, zanotuj czas i usuń jedną dokładną nazwę. Obserwuj pojawienie się nowego Poda.

  3. Przeskaluj API do trzech replik.
    Pokaż przykład polecenia

    Wykonaj kubectl scale deployment/api --replicas=3, a potem kubectl rollout status deployment/api.

  4. Sprawdź endpoints Service oraz odpowiedzi aplikacji.
    Pokaż przykład polecenia

    kubectl get endpointslice -l kubernetes.io/service-name=api powinno pokazać trzy gotowe adresy. Kilkukrotnie odpytaj endpoint API.

kubectl get pods -w
kubectl delete pod POD_API
kubectl scale deployment/api --replicas=3
kubectl get pods -l app=api
kubectl get endpointslice -l kubernetes.io/service-name=api
Self-healing oznacza, że kontrolery Kubernetes stale porównują stan faktyczny z zadeklarowanym i odtwarzają brakujące Pody. Deployment odtwarza liczbę replik, a Service odnajduje gotowe Pody przez selektor. Samo skalowanie bazy danych w ten sposób byłoby błędne. Wróć do słowniczka ↑

Sprawdź w Rancher Desktop

  1. Otwórz Deployment api przed usunięciem Poda i obserwuj liczbę replik.
  2. Po skalowaniu odśwież widok Podów oraz Service api.
  3. W widoku Containers sprawdź, że pojawił się trzeci kontener API; w Stats możesz porównać użycie zasobów replik.

Oczekiwany widok: Deployment i lista Podów pokazują trzy gotowe repliki, a Service kieruje ruch do trzech endpointów.

Wersje

Zadanie 11 — rollout i kontrolowany błąd

Rollout to kontrolowane wdrażanie nowej wersji przez Deployment, a rollback — powrót do wcześniejszej rewizji, gdy aktualizacja się nie powiedzie. Wróć do słowniczka ↑

  1. Zapisz stan początkowy oraz historię Deployment API.
    Pokaż przykład polecenia

    Wykonaj kubectl get deployment,replicaset,pods -l app=api oraz kubectl rollout history deployment/api.

  2. Ustaw nieistniejący tag 1.1.0-broken.
    Pokaż przykład polecenia

    Użyj kubectl set image deployment/api api=mission-control-api:1.1.0-broken. Pierwsze api po ukośniku jest nazwą kontenera.

  3. Zaobserwuj, że nowe Pody nie startują, a gotowe repliki pozostają w ruchu.
    Pokaż sposób obserwacji

    Uruchom kubectl rollout status deployment/api --timeout=60s oraz kubectl get pods -l app=api. Spodziewaj się błędu nowego Poda, ale nie zera gotowych replik.

  4. Znajdź przyczynę w describe i Events.
    Pokaż przykład polecenia

    Wykonaj kubectl describe pod NAZWA_BŁĘDNEGO_PODA i sprawdź sekcję Events. Szukaj ErrImageNeverPull.

  5. Wykonaj rollback i potwierdź powrót do zdrowego stanu.
    Pokaż przykład polecenia

    kubectl rollout undo deployment/api, następnie kubectl rollout status deployment/api i sprawdzenie, czy wszystkie repliki są Ready.

kubectl rollout history deployment/api
kubectl set image deployment/api api=mission-control-api:1.1.0-broken
kubectl rollout status deployment/api --timeout=60s
kubectl get pods
kubectl describe deployment api
kubectl rollout undo deployment/api
kubectl rollout status deployment/api

Oczekiwany błąd to problem pobrania lokalnie nieistniejącego obrazu. Nie zmieniaj imagePullPolicy, aby „naprawić” eksperyment.

Sprawdź w Rancher Desktop

  1. W Deployment api obserwuj pojawienie się nowego ReplicaSetu i Poda.
  2. Otwórz błędny Pod i jego Events.
  3. Po rollbacku sprawdź, czy błędny ReplicaSet został przeskalowany do zera, a wersja 1.0.0 ponownie ma wszystkie gotowe repliki.

Oczekiwany widok: nowy Pod ma stan ErrImageNeverPull, natomiast stare Pody nadal są Ready. Po rollbacku Deployment wraca do zdrowego stanu.

Pytania do samokontroli

  1. Dlaczego API używa hosta db, a nie localhost?
    Odpowiedź

    Każdy Pod ma własną przestrzeń sieciową. Nazwa Service db jest rozwiązywana przez DNS klastra do stabilnego adresu usługi bazy.

  2. Dlaczego depends_on nie ma bezpośredniego odpowiednika?
    Odpowiedź

    Kubernetes stale uzgadnia stan, a Pody mogą być odtwarzane w dowolnej kolejności. Gotowość opisują sondy, a aplikacja powinna ponawiać zależności.

  3. Czym różni się ConfigMap od Secret?
    Odpowiedź

    Oba dostarczają konfigurację. Secret ma osobny typ, kontrolę dostępu i może korzystać z szyfrowania w etcd, lecz Base64 samo nie zapewnia poufności.

  4. Dlaczego PVC nie jest backupem?
    Odpowiedź

    Wolumen utrzymuje dane poza Podem, ale błąd aplikacji, usunięcie wolumenu lub awaria storage nadal może je zniszczyć. Backup ma osobną kopię i procedurę odtwarzania.

  5. Co robi readiness, a co liveness?
    Odpowiedź

    Readiness decyduje o kierowaniu ruchu. Liveness może spowodować restart kontenera, gdy proces nie odzyskuje sprawności.

  6. Dlaczego Service nie wskazuje Podów po nazwie?
    Odpowiedź

    Pody są wymienne. Service wybiera dynamiczny zbiór gotowych Podów przez etykiety i selektor.
