Laboratorium 04 / Ansible / WSL

Skonfiguruj Debiana z Ubuntu przez Ansible

Ubuntu WSL będzie control node, a Debian WSL hostem zarządzanym przez SSH. Uzupełnisz szkielet playbooka, zainstalujesz wymagane narzędzia i udowodnisz, że konfiguracja jest powtarzalna.

Cel i sposób pracy

Nie wykonujesz instalacji ręcznie na Debianie. Opisujesz oczekiwany stan w projekcie ansible-lab-start, a Ansible wykonuje zadania z Ubuntu.

Ubuntu WSLcontrol nodeAnsibleinventory i playbook
→
Debian WSLmanaged nodeSSH + Pythongh, .NET, Java, Maven, Node.js
  • Wykonuj zadania po kolei i zapisuj zmiany w projekcie.
  • Wszystkie polecenia Ansible uruchamiaj z katalogu projektu.
  • Ścieżki są względne względem ansible-lab-start.
  • Nie zapisuj haseł ani kluczy prywatnych w repozytorium.
Ważne: Become password to hasło użytkownika na Debianie używane przez sudo.

Przygotowanie środowiska WSL

W laboratorium używasz dwóch dystrybucji WSL 2: Ubuntu jako control node i Debiana jako managed node. Wykonuj polecenia w odpowiedniej dystrybucji.

Windows PowerShellinstalacja i lista dystrybucjikontrola wersji WSL
→
Ubuntu + Debian WSLUbuntu: Ansible i SSH clientDebian: SSH server i Python

1. Zainstaluj dystrybucje WSL

W PowerShell uruchomionym jako administrator sprawdź dostępne dystrybucje i zainstaluj Ubuntu oraz Debiana.

wsl --set-default-version 2
wsl --list --online
wsl --install -d Ubuntu-24.04
wsl --install -d Debian
wsl --list --verbose
Nazwy użytkowników ustal od razu: przy pierwszym uruchomieniu Ubuntu wpisz nazwę ansible-control; przy pierwszym uruchomieniu Debiana wpisz nazwę ansible-managed. Nie używaj tutaj domyślnej nazwy typu student, aby role obu maszyn były jednoznaczne.
Pokaż podpowiedź

Przy pierwszym uruchomieniu Ubuntu utwórz użytkownika ansible-control, a przy pierwszym uruchomieniu Debiana utwórz użytkownika ansible-managed. Ustaw hasła i zapamiętaj je do operacji sudo. W wsl --list --verbose kolumna VERSION powinna mieć wartość 2.

2. Przygotuj Ubuntu jako control node

Uruchom Ubuntu i zainstaluj Ansible oraz klienta SSH.

wsl -d Ubuntu-24.04
sudo apt update
sudo apt install -y ansible openssh-client
ansible --version
ssh -V

3. Przygotuj Debiana jako managed node

W osobnym terminalu uruchom Debiana. Zainstaluj serwer SSH, Pythona i sudo, a następnie uruchom usługę SSH.

wsl -d Debian
sudo apt update
sudo apt install -y openssh-server python3 sudo
sudo service ssh start
sudo service ssh status
hostname -I
Adres IP Debiana może zmienić się po ponownym uruchomieniu WSL. Do inventory wpisuj aktualny adres z hostname -I.

4. Skonfiguruj klucz SSH

W Ubuntu utwórz klucz Ed25519 i dodaj jego klucz publiczny do użytkownika na Debianie.

# Ubuntu
ssh-keygen -t ed25519
ssh-copy-id ansible-managed@ADRES_DEBIANA
ssh ansible-managed@ADRES_DEBIANA 'python3 --version'
Jeśli nie masz ssh-copy-id

Na Debianie utwórz katalog ~/.ssh i dopisz zawartość pliku Ubuntu ~/.ssh/id_ed25519.pub do ~/.ssh/authorized_keys. Ustaw prawa katalogu na 700, a pliku na 600.

5. Sprawdź gotowe środowisko

# Ubuntu
ssh ansible-managed@ADRES_DEBIANA 'hostname && python3 --version'
ansible all -i 'ADRES_DEBIANA,' -u ansible-managed -m ansible.builtin.ping
Oczekiwany rezultat: zwykłe SSH wykonuje komendę na Debianie, a Ansible zwraca pong. Dopiero teraz przejdź do inventory projektu.

Przygotowanie

Użytkownicy są tworzeni podczas pierwszego uruchomienia WSL: Ubuntu używa ansible-control, a Debian ansible-managed. Nie twórz później drugich kont o innych nazwach.
  • Ubuntu WSL ma Ansible.
  • Debian WSL ma działający SSH.
  • Z Ubuntu logujesz się do Debiana kluczem SSH.
  • Użytkownik może wykonać sudo.
  • Na Debianie działa Python 3.
# Ubuntu WSL
ansible --version
ssh -V

# Debian WSL
hostname -I
sudo systemctl status ssh
python3 --version
Nie przechodź dalej z błędem SSH. Sprawdź adres IP, użytkownika, klucz i port 22.

Konfiguracja hosta

Zadanie 1 — inventory i SSH

Uzupełnij inventory.yml adresem Debiana z hostname -I, użytkownikiem, portem i kluczem SSH.

all:
  hosts:
    debian_wsl:
      ansible_host: ADRES_DEBIANA
      ansible_user: ansible-managed
      ansible_connection: ssh
      ansible_port: 22
      ansible_ssh_private_key_file: ~/.ssh/id_ed25519
ansible-inventory -i inventory.yml --graph
ansible all -i inventory.yml -m ansible.builtin.ping
Pokaż podpowiedź diagnostyczną

no such identity oznacza brak klucza. Permission denied oznacza problem z authorized_keys lub użytkownikiem.

Playbook

Zadanie 2 — pierwszy playbook

W site.yml wybierz host debian_wsl, włącz sudo i uruchom rolę common.

- name: Przygotuj Debiana do laboratorium Ansible
  hosts: debian_wsl
  become: true
  roles:
    - common
ansible-playbook -i inventory.yml site.yml --check --ask-become-pass
Pokaż oczekiwany rezultat

Playbook powinien połączyć się z Debianem i zebrać Facts.

Zmienne

Zadanie 3 — wersje poza zadaniami

W group_vars/all.yml zdefiniuj wersję Node.js, pakiety Java, Maven i .NET oraz ścieżkę raportu.

nodejs_major_version: "20"
java_package: openjdk-21-jdk
maven_package: maven
dotnet_channel: "10.0"
report_path: /tmp/ansible-lab-report.txt
Rola

Zadanie 4 — pakiety bazowe

W roles/common/tasks/main.yml dodaj zadanie instalujące wymagania APT przez moduł ansible.builtin.apt.

- name: Zainstaluj wymagania APT
  ansible.builtin.apt:
    name:
      - ca-certificates
      - curl
      - gnupg
      - python3-apt
    state: present
    update_cache: true

Jeśli check mode zgłasza brak python3-apt, wykonaj pierwszy przebieg normalnie.

Po zmianie uruchom playbook:
ansible-playbook -i inventory.yml site.yml --check --diff --ask-become-pass
ansible-playbook -i inventory.yml site.yml --ask-become-pass

Najpierw sprawdzasz przewidywane zmiany, a dopiero potem instalujesz pakiety bazowe.

Sprawdź na Debianie

Z Ubuntu: sprawdź rezultat z control node przez Ansible.

ansible debian_wsl -i inventory.yml -m ansible.builtin.command -a 'dpkg -s python3-apt'

W konsoli Debiana: wykonaj sprawdzenie bezpośrednio na hoście zarządzanym.

dpkg -s python3-apt | grep Status
Narzędzia developerskie

Zadanie 5 — narzędzia developerskie

Rozszerz rolę o GitHub CLI, .NET SDK, OpenJDK, Maven oraz Node.js. Pakiety dostępne w Debianie instaluj modułem ansible.builtin.apt, a .NET SDK instaluj oficjalnym skryptem opisanym niżej.

Instrukcja instalacji: użyj repozytoriów Debiana dla gh, Node.js, npm, Java i Maven. Nie dodawaj kluczy GPG ani zewnętrznych repozytoriów APT w zadaniu podstawowym.

Zmienne: przed wykonaniem zadania sprawdź plik group_vars/all.yml. To z niego pochodzą java_package, maven_package, dotnet_channel oraz report_path. Ansible ładuje ten plik automatycznie dla wszystkich hostów.

  1. Odśwież cache APT modułem ansible.builtin.apt.
  2. Zainstaluj gh, nodejs, npm, openjdk-21-jdk i maven jednym lub kilkoma zadaniami apt.
  3. .NET SDK zainstaluj oficjalnym skryptem dotnet-install.sh, ponieważ nie ma go w standardowym repozytorium Debiana.
  4. Po instalacji sprawdź wszystkie wersje bezpośrednio na Debianie.
Pokaż instrukcję wykonania
  1. W roles/common/tasks/main.yml dodaj zadanie ansible.builtin.apt. Pakiety z repozytoriów Debiana instaluj deklaratywnie: 
    - name: Zainstaluj narzędzia z Debiana
  ansible.builtin.apt:
    name:
      - gh
      - nodejs
      - npm
      - "{{ java_package }}"
      - "{{ maven_package }}"
    state: present
    update_cache: true
    Moduł apt sprawdza, czy pakiet jest już obecny, więc kolejne uruchomienie nie instaluje go ponownie.
  2. Pobierz skrypt instalacyjny .NET na Debiana: 
    - name: Pobierz instalator .NET
  ansible.builtin.get_url:
    url: https://dot.net/v1/dotnet-install.sh
    dest: /tmp/dotnet-install.sh
    mode: '0755'
    get_url pobiera plik na host zarządzany i nadaje mu prawa wykonywania.
  3. Uruchom skrypt tylko wtedy, gdy .NET nie jest jeszcze zainstalowany: 
    - name: Zainstaluj .NET SDK
  ansible.builtin.command: "/tmp/dotnet-install.sh --channel {{ dotnet_channel }} --install-dir /usr/share/dotnet"
  args:
    creates: /usr/share/dotnet/dotnet
    args.creates chroni przed ponownym uruchomieniem instalatora.
  4. Udostępnij polecenie wszystkim użytkownikom: 
    - name: Udostępnij polecenie dotnet
  ansible.builtin.file:
    src: /usr/share/dotnet/dotnet
    dest: /usr/local/bin/dotnet
    state: link
    Link w /usr/local/bin pozwala wywołać dotnet bez podawania pełnej ścieżki.
  5. Po zastosowaniu zmian sprawdź wersje lokalnie w konsoli Debiana oraz z Ubuntu przez Ansible.
Po zmianie uruchom playbook:
ansible-playbook -i inventory.yml site.yml --check --diff --ask-become-pass
ansible-playbook -i inventory.yml site.yml --ask-become-pass

Po normalnym wykonaniu przejdź do bloku „Sprawdź na Debianie”.

Weryfikacja

Zadanie 6 — Facts, register i asercje

Dodaj asercję Debiana x86_64 i sprawdzenie Node.js z użyciem register.

- name: Sprawdź system zarządzany
  ansible.builtin.assert:
    that:
      - ansible_distribution == 'Debian'
      - ansible_architecture == 'x86_64'
    fail_msg: Laboratorium wymaga Debiana x86_64.

- name: Sprawdź Node.js
  ansible.builtin.command: node --version
  register: node_version
  changed_when: false
  failed_when: not node_version.stdout.startswith('v' ~ nodejs_major_version ~ '.')
Pokaż oczekiwany rezultat

Poprawny host i wersja dają ok. Fałszywa asercja zatrzymuje playbook.

Rozszerz asercje dla wszystkich narzędzi

Masz już przykład dla Node.js. Dodaj teraz analogiczne zadania dla pozostałych narzędzi. Poniżej znajduje się jeden przykład — dopisz resztę samodzielnie.

- name: Sprawdź wersję .NET
  ansible.builtin.command: dotnet --version
  register: dotnet_version
  changed_when: false
  failed_when: dotnet_version.rc != 0

- name: Potwierdź obecność .NET
  ansible.builtin.assert:
    that:
      - dotnet_version.rc == 0
      - dotnet_version.stdout | trim | length > 0
    fail_msg: .NET SDK nie jest dostępny na Debianie.

Dopisz podobne pary zadań dla gh, npm, Java, Maven i Node.js. Każde sprawdzenie powinno używać register, changed_when: false oraz assert.

Po zmianie uruchom playbook:
ansible-playbook -i inventory.yml site.yml --check --diff --ask-become-pass
ansible-playbook -i inventory.yml site.yml --ask-become-pass

Asercje i sprawdzenia nie powinny wprowadzać zmian na hoście; ich zadaniem jest potwierdzenie założeń.

Raport

Zadanie 7 — raport i handler

Utwórz na Debianie raport wersji wszystkich narzędzi. Dodaj plik konfiguracyjny i handler uruchamiany po jego zmianie.

- name: Zapisz znacznik konfiguracji
  ansible.builtin.copy:
    dest: /etc/ansible-lab.conf
    content: "Ansible laboratory configured\n"
  notify: Sprawdź konfigurację laboratorium
# roles/common/handlers/main.yml
- name: Sprawdź konfigurację laboratorium
  ansible.builtin.command: test -s /etc/ansible-lab.conf
  changed_when: false
Po zmianie uruchom playbook:
ansible-playbook -i inventory.yml site.yml --check --diff --ask-become-pass
ansible-playbook -i inventory.yml site.yml --ask-become-pass

Dopiero po zastosowaniu zmian sprawdź raport i plik handlera na Debianie.

Bezpieczne wykonanie

Zadanie 8 — check mode i idempotencja

Wykonaj dry-run, zastosuj konfigurację, a następnie uruchom ją drugi raz.

ansible-playbook -i inventory.yml site.yml --check --diff --ask-become-pass
ansible-playbook -i inventory.yml site.yml --ask-become-pass
ansible-playbook -i inventory.yml site.yml --ask-become-pass
Oczekiwany rezultat: pierwszy przebieg wprowadza zmiany, a drugi raportuje głównie ok.

Sprawdź na Debianie

Z Ubuntu: sprawdź rezultat z control node przez Ansible.

ansible debian_wsl -i inventory.yml -m ansible.builtin.command -a 'test -s /tmp/ansible-lab-report.txt'
ansible debian_wsl -i inventory.yml -m ansible.builtin.command -a 'test -s /etc/ansible-lab.conf'

W konsoli Debiana: wykonaj sprawdzenie bezpośrednio na hoście zarządzanym.

test -s /tmp/ansible-lab-report.txt && echo 'raport OK'
test -s /etc/ansible-lab.conf && echo 'konfiguracja OK'
Dowód zmiany

Zadanie 9 — sprawdź, czy Debian się zmienił

Porównaj stan Debiana przed i po wykonaniu playbooka. Potwierdź zmianę bezpośrednio na hoście zarządzanym oraz sprawdź wynik drugiego przebiegu.

# przed zmianą — oczekiwany brak pliku
ansible debian_wsl -i inventory.yml -m ansible.builtin.command -a 'test -e /tmp/ansible-lab-report.txt'

# zastosowanie konfiguracji
ansible-playbook -i inventory.yml site.yml --ask-become-pass

# dowód zmiany na Debianie
ansible debian_wsl -i inventory.yml -m ansible.builtin.command -a 'hostname'
ansible debian_wsl -i inventory.yml -m ansible.builtin.command -a 'cat /tmp/ansible-lab-report.txt'
ansible debian_wsl -i inventory.yml -m ansible.builtin.stat -a 'path=/tmp/ansible-lab-report.txt'

# ponowne wykonanie — oczekuj głównie ok
ansible-playbook -i inventory.yml site.yml --ask-become-pass
Oczekiwany dowód: pierwszy przebieg tworzy raport na Debianie, raport zawiera fakty systemu, a drugi przebieg nie tworzy ponownej zmiany.
