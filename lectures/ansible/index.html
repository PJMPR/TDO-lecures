Architektura

Kontroler wysyła zadania do hostów

control node
WSL + Ansible
SSH + Python
lub local
managed node
agent Ubuntu 24.04

Na hoście zarządzanym nie instalujemy demona Ansible. W wariancie WSL kontroler i host to ta sama dystrybucja.

Push model

Ansible nie wymaga własnego agenta

  • kontroler odczytuje inventory i playbook,
  • łączy się przez SSH albo używa połączenia lokalnego,
  • uruchamia moduły przez Python na hoście,
  • zbiera wynik każdego zadania.

GitHub Actions runner jest osobnym agentem wykonawczym. Ansible może go przygotować i zarejestrować.

Demo 01 // środowisko

Pracujemy na lokalnym Ubuntu w WSL

  1. 1wsl --install -d Ubuntu-24.04
  2. 2wsl -d Ubuntu-24.04

Demo używa połączenia lokalnego, więc nie potrzebujemy SSH ani osobnego hosta zarządzanego.

Demo 02 // control node

Instalujemy Ansible w Ubuntu

  1. 1sudo apt update
  2. 2sudo apt install -y ansible
  3. 3ansible --version

Demo 04 // pierwszy kontakt

Najpierw sprawdzamy inventory i moduł ping

  1. 1ansible-inventory -i inventory.yml --graph
  2. 2ansible all -i inventory.yml -m ansible.builtin.ping
Pojęcie 02

Playbook opisuje przebieg konfiguracji

  hosts: build_agents
  become: true

    - common
    - dotnet
    - node
    - terraform
    - validation

Playbook wybiera hosty i uruchamia zadanie

  2. 2 hosts: all

  4. 4 tasks:
Pojęcie 03

Task wywołuje moduł z argumentami

- name: Zainstaluj pakiety bazowe
  ansible.builtin.apt:
    name:
      - git
      - unzip
    state: present
    update_cache: true

apt zna stan pakietów. Surowa komenda nie daje tej samej gwarancji.

Najważniejsza własność

Demo 06 // moduł apt

Instalujemy GitHub CLI deklaratywnie

  1. 1- name: Zainstaluj GitHub CLI
  2. 2 ansible.builtin.apt:
  3. 3 name: gh
  4. 4 state: present
  5. 5 update_cache: true

Polecenie wykonamy z katalogu projects/ansible-demo-start.

Raport

Każde zadanie kończy się stanem

ok

Stan już był poprawny.

changed

Moduł wykonał zmianę.

failed

Play zatrzymał się lub obsłużył błąd.

Demo 07 // konwergencja

Uruchamiamy playbook dwa razy

  1. 1ansible-playbook -i inventory.yml site.yml \
  2. 2 --ask-become-pass
  3. 3ansible-playbook -i inventory.yml site.yml --ask-become-pass

To jest praktyczna demonstracja idempotencji: pierwszy przebieg instaluje, drugi potwierdza stan.

Pojęcie 04

Zmienne oddzielają politykę od mechanizmu

dotnet_sdk_package: dotnet-sdk-10.0
node_version: 24.11.1
terraform_version: 1.17.1-1
angular_cli_version: 21.0.0

Rola opisuje instalację. Wersje można zmienić w jednym miejscu.

Pojęcie 05

Facts opisują wykryty host

- name: Wymagaj Ubuntu 24.04 na x86_64
  ansible.builtin.assert:
    that:
      - ansible_distribution == 'Ubuntu'
      - ansible_distribution_version == '24.04'
      - ansible_architecture == 'x86_64'
Pojęcie 06

Handler reaguje tylko na rzeczywistą zmianę

- name: Zapisz konfigurację usługi
  ansible.builtin.template:
    src: agent.conf.j2
    dest: /etc/agent.conf
  notify: Uruchom ponownie usługę

Ansible Vault

Szyfruje pliki zmiennych przechowywane w repozytorium.

ansible-vault create group_vars/vault.yml
ansible-playbook site.yml --ask-vault-pass
