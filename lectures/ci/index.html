CI i SDLC

Od zmiany w kodzie do informacji, której zespół może zaufać.

Najpierw proces. Potem pierwszy działający workflow, jego mechanizmy i reguły bezpiecznej integracji.

Software Development Life Cycle

Rozwój to pętla

Potrzeby użytkowników prowadzą do zmian. Wyniki testów, review i obserwacje z eksploatacji wracają do zespołu.

  • Etapy nie muszą być osobnymi, zamkniętymi fazami.
  • Krótka iteracja może przejść przez cały cykl.
  • CI skraca pętlę informacji zwrotnej podczas pracy nad zmianą.
Continuous Integration

Mała zmiana. Szybka odpowiedź.

Integruj często

Krótkie gałęzie i niewielkie zmiany ograniczają liczbę możliwych przyczyn problemu.

Sprawdzaj automatycznie

Build i testy uruchamiają się według tych samych reguł dla kolejnych zmian.

Reaguj na wynik

Czerwony wynik wymaga diagnozy i poprawki. Sam plik YAML nie tworzy praktyki CI.

Błąd wykryty po kilku minutach łatwiej połączyć z konkretną zmianą niż problem odkryty po tygodniu.

Co obejmuje sprawdzenie?

Testy mają różny zakres

Jednostkowe

Mały fragment logiki. Zależności często zastępują duble. Zwykle krótki czas i precyzyjna diagnoza.

Integracyjne

Współpraca elementów, np. API i bazy danych. Sprawdzają granice, których nie obejmuje test z mockiem.

End-to-end

Scenariusz użytkownika przez cały system, często z przeglądarką. Szerszy sygnał, większy koszt środowiska i diagnozy.

Lint i analiza statyczna uzupełniają testy. Zielony wynik dowodzi przejścia skonfigurowanych sprawdzeń, nie braku wszystkich błędów.

02 // Współpraca w Git

Dokąd trafia zmiana?

Najpierw ustalamy model integracji. Dopiero potem konfigurujemy automatyzację.

GitHub FlowMerge, squash, fast-forwardGit Flow

Gałąź jest nazwanym wskaźnikiem na commit. Nazwy main i develop otrzymują znaczenie od zespołu, nie od samego Gita.

Jedna główna linia pracy

GitHub Flow: main + feature

  • Zmianę zaczynamy z aktualnego main; PR można otworzyć jeszcze jako draft.
  • Kolejne commity aktualizują ten sam PR i jego sprawdzenia.
  • Po akceptacji integrujemy zmianę, usuwamy feature i utrzymujemy main gotowy do wydania.

GitHub Flow

Ta sama zmiana // inna historia

Merge zachowuje gałąź. Squash scala zmianę.

Merge commit

M ma dwóch rodziców. Commity F1 i F2 zachowują tożsamość oraz relację z gałęzią.

Squash and merge

S ma jednego rodzica. Zawiera łączną zmianę PR-a, ale nie włącza F1 i F2 jako przodków main.

Bez nowego commita scalenia

Fast-forward przesuwa wskaźnik

git switch main
git pull --ff-only

--ff-only odmawia integracji rozbieżnej historii. Chroni np. wtedy, gdy na lokalnym main zostały własne commity, a zdalny main też poszedł naprzód.

To kontrola historii commitów, nie sposób zapisywania niezacommitowanych plików. GitHub „Rebase and merge” jest inną operacją niż lokalny fast-forward.

Main + develop + gałęzie wydania

Release oddziela stabilizację od rozwoju

Feature: develop → feature → develop. Release: develop → release → main i develop, żeby poprawki nie zginęły.

Naprawa poza bieżącym rozwojem

Hotfix wraca do obu linii

Nie trzeba wydawać całego niestabilnego develop, aby poprawić błąd produkcyjny.

Przy aktywnej gałęzi release hotfix przenosimy także do niej; późniejsze scalenie release zasili develop.

Proces powinien pasować do sposobu wydawania

Więcej gałęzi ≠ lepsza integracja

GitHub Flow

Main i krótkie feature branches. Pasuje do częstej integracji niewielkich zmian.

Checks i review chronią powrót zmiany do main.

Git Flow

Osobne linie rozwoju i stabilizacji. Może pasować do wersjonowanych wydań przygotowywanych przez dłuższy czas.

Checks muszą chronić również właściwe gałęzie develop i release.

Autor Git Flow sam zaleca prostszy model dla oprogramowania dostarczanego ciągle.

04 // Pierwsze uruchomienie

Od kilku kluczy do działającego workflow

YAML opisuje strukturę. Schemat GitHub Actions nadaje tej strukturze znaczenie.

Mapy i listyHello CIEdytor i walidacja
Fragment struktury workflow

Mapa ma klucze. Lista ma elementy.

jobs:
  hello:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Cześć"
      - run: pwd
  • klucz: wartość tworzy wpis w mapie.
  • hello jest kluczem mapy jobs.
  • - rozpoczyna element listy steps.
  • Wcięcia ze spacji pokazują zagnieżdżenie.

Workflow zapisujemy w repozytorium jako plik .github/workflows/hello.yml lub .yaml.

Cały plik .github/workflows/hello.yml

Pierwszy workflow: Hello CI

name: Hello CI
on: push
permissions: {}
jobs:
  hello:
    name: Powitanie
    runs-on: ubuntu-24.04
    steps:
      - name: Wiadomość
        shell: bash
        run: echo "CI działa!"
      - name: System
        shell: bash
        run: uname -s

Po wysłaniu pliku do GitHuba zdarzenie push uruchomi jedno zadanie z dwoma krokami.

Nie potrzebujemy repozytorium na dysku runnera ani uprawnień do API. Wykonujemy tylko polecenia powłoki.

System wybraliśmy jawnie: ubuntu-24.04.

Kiedy cytować wartość?

Cudzysłów chroni znaczenie tekstu

name: "Build: API #1"
env:
  FLAG: "false"
  NOTICE: "! to jest tekst"
  LABEL: 'Raport #1'

# Komentarz, nie wartość

  • false jest wartością logiczną, a "false" tekstem.
  • : ze spacją może wprowadzić kolejny wpis mapy.
  • # rozpoczyna komentarz, gdy stoi poza cytowanym skalarem w miejscu komentarza, np. po spacji.
  • "Raport #1" zachowuje znak # jako część tekstu.
Dwie reprezentacje tekstu

05 // Anatomia wykonania

Co uruchomiliśmy w Hello CI?

Oddziel definicję procesu, konkretne wykonanie i środowisko, w którym działa kod.

Workflow i runJob i runnerStep i action
Definicja ≠ wykonanie

Workflow opisuje. Run jest zdarzeniem w historii.

Workflow

→

→

kolejne czynności

  • Step uruchamia polecenie run albo komponent uses.
  • Action to komponent wywołany w kroku, nie dodatkowy poziom między jobem a runnerem.
Nie każde id jest polem id w YAML

name to etykieta. id to identyfikator.

name: Kontrola projektu
run-name: Sprawdzenie zmiany
jobs:
  verify:
    name: Build i testy
    runs-on: ubuntu-24.04
    steps:
      - name: Wersja systemu
        id: system
        run: uname -s
  • name workflow jest widoczne na liście Actions.
  • run-name opisuje konkretne uruchomienie.
  • verify jest identyfikatorem joba — kluczem mapy.
  • system jest opcjonalnym id kroku.
  • GitHub nadaje też własne identyfikatory workflow i runs używane w API.
Kolejność w pliku nie jest zależnością jobs

Kroki kolejno. Jobs mogą równolegle.

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Krok 1"
      - run: echo "Krok 2"
  docs:
    runs-on: ubuntu-24.04
    steps:
      - run: echo "Osobny job"

W lint drugi krok czeka na pierwszy. Oba korzystają z workspace tego samego joba.

lint i docs mogą działać jednocześnie, jeśli dostępne są runnery.

Standardowe joby GitHub-hosted mają osobne środowiska. Plik utworzony w jednym nie pojawia się automatycznie w drugim.

Dwie osobne odpowiedzialności

Kod i narzędzia przygotowujemy osobno

  • Do samego echo albo odczytu API checkout nie jest potrzebny.

Metadata syntax — runs

Dwa różne zastosowania kontenerów

Gdzie działa skrypt? Gdzie działa baza?

container — środowisko joba

runs-on: ubuntu-24.04
container: node:24-bookworm
steps:
  - run: node --version

Kroki run wykonują się wewnątrz kontenera joba. Domyślną powłoką jest tu sh, nie Bash.

services — proces obok joba

runs-on: ubuntu-24.04
services:
  postgres:
    image: postgres:17
    env:
      POSTGRES_PASSWORD: ci-only
    ports: ['5432:5432']

Skrypt działa na runnerze, baza w osobnym kontenerze. Tutaj łączy się przez localhost:5432.

Gdy sam job działa w kontenerze, usługę osiąga po nazwie postgres:5432. Przed testami trzeba zaczekać na gotowość bazy, np. przez healthcheck.

  • To nie jobs.<id>.container ani długotrwała usługa z services.

06 // Kiedy i dla jakiego kodu?

Trigger wybiera więcej niż moment startu

Zdarzenie określa kontekst, sprawdzaną rewizję i granicę zaufania.

Push i PRSchedule i dispatchRef, SHA i merge ref
Przykład dla main i krótkich feature branches

PR przed integracją. Push po integracji.

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  • push sprawdza commit wysłany do main, także po merge.
  • pull_request domyślnie reaguje na otwarcie, ponowne otwarcie i synchronizację PR-a.
  • Filtr pull_request.branches dotyczy gałęzi docelowej, nie gałęzi autora.

W Git Flow trzeba uwzględnić również PR-y do develop lub release. Push na każdą gałąź obok triggera PR może tworzyć dwa runs dla jednej zmiany.

Podobna nazwa // inna granica zaufania

Uwaga: pull_request_target

pull_request

Do budowania i testowania proponowanej zmiany. Fork PR ma domyślnie ograniczony token i nie otrzymuje sekretów repozytorium.

pull_request_target

Workflow w kontekście bazowego repozytorium. Może mieć dostęp do prawa zapisu i sekretów. Służy np. do zaufanej automatyzacji metadanych.

Nie pobieraj i nie wykonuj niezaufanego kodu PR-a z uprawnieniami bazowego repozytorium.

Zmiana triggera nie jest bezpieczną „naprawą” braku sekretów w zwykłym PR.

pull_request_target — kontekst i ostrzeżenia

Ten sam commit to dopiero początek

.github/scripts/required.cjs

Błędny lub brakujący wynik nie przechodzi

const results = JSON.parse(process.env.RESULTS);
if (results.changes?.result !== 'success') {
  throw new Error('Nie udało się ustalić planu');
}
for (const name of ['frontend', 'backend']) {
  const needed = results.changes.outputs?.[name];
  const result = results[name]?.result;
  const accepted = (needed === 'true' && result === 'success')
    || (needed === 'false' && result === 'skipped');
  if (!accepted) throw new Error(`Niespełniony warunek: ${name}`);
}

To jawna polityka: potrzebna praca musi zakończyć się sukcesem, a niepotrzebna może być pominięta.

Jak każdy element CI, skrypt gate i konfigurację workflow chronimy review. Zielony gate nie pomoże, jeśli PR może dowolnie usunąć jego kontrole.

Sprawdzamy nie tylko wynik testu, ale też pochodzenie kodu, danych i uprawnień.

SekretyDane zamiast koduRef i aktualizacje
Najmniejszy potrzebny dostęp

Build nie potrzebuje prawa publikacji

  • Build i testy dostają odczyt kodu, nie domyślne write-all.
  • Zapis przez API wydzielamy do joba, który go rzeczywiście potrzebuje.
  • Nie przekazujemy sekretów produkcyjnych do testów z tymczasową bazą.
  • Sekrety nie trafiają do Git, outputs, artefaktów ani cache. Maskowanie logów jest tylko dodatkową ochroną.
  • Fork PR i kod zależności traktujemy jako niezaufane. Zgoda na uruchomienie nie czyni kodu bezpiecznym.

Reusable workflow nie może podnieść uprawnień tokena callera. Sekrety przekazuje się przez jawny interfejs; samo env nie tworzy takiego kontraktu.

Tytuł PR-a jest wejściem użytkownika

Nie interpoluj danych do źródła skryptu

Co naprawdę dowodzi zbudowany PDF?

Brak błędu kompilacji ≠ gotowa praca

Błąd

Nieznane polecenie albo brak wymaganego pliku może zatrzymać kompilację i zablokować publikację.

Ostrzeżenie

Brakujące cytowanie lub odwołanie może pozostawić PDF i kod sukcesu. -halt-on-error nie zamienia każdego warning w błąd.

Jeśli zespół wymaga braku określonych ostrzeżeń, dopisuje jawną kontrolę logu. Ocena treści naukowej nadal należy do człowieka.

Ten sam model poza LaTeX

Automatyzuj sprawdzalne twierdzenia

Dokumentacja

Build, kontrola linków i brakujących zasobów. HTML lub PDF jako wynik do obejrzenia.

Błąd sieci do zewnętrznej strony trzeba odróżnić od nieprawidłowego linku.

Notebook lub raport

Wykonanie od początku, z określonymi danymi, bibliotekami i ziarnem losowym.

Brak ukrytego stanu sesji jest weryfikowalny; poprawność metody badawczej wymaga osobnej oceny.

W każdym przypadku ustalamy: wejście → polecenie → warunek błędu → wynik → odbiorca.
